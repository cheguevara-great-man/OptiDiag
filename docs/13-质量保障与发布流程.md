# 质量保障与发布流程

## 1. 质量不是“能编译”

OptiDiag 的质量证据分为五层：

1. 编译器：Nullable、Warnings as Errors、确定性构建；
2. 单元测试：公式、码表、字段、风险策略；
3. 集成测试：会话、分页、Dump、写入和模拟器；
4. UI 冒烟：窗口、主题、下拉框、关键对话框；
5. 真实硬件验证：只有拿到具体设备后才能完成。

任何一层通过都不能代替下一层。

## 2. 测试分类

### Core

覆盖会话、协议检测、I²C 日志、Dump、比较、安全写入、设置和版本解析。

### SFF-8472

覆盖身份、DDM、校准、告警、时延、RPM 和 SFF-8690。

### CMIS

覆盖版本差异、页面/Bank、监控、VDM、CDB、固件和 5.4 扩展。

测试数量不是唯一指标。每项测试应说明一个失败会造成什么用户风险。

## 3. 本地验证

```powershell
& "$env:USERPROFILE\.dotnet\dotnet.exe" restore .\OptiDiag.sln
& "$env:USERPROFILE\.dotnet\dotnet.exe" build .\OptiDiag.sln -c Release --no-restore
& "$env:USERPROFILE\.dotnet\dotnet.exe" test .\OptiDiag.sln -c Release --no-build
```

测试进程必须以非零退出码报告失败。不能只打印 `FAILED` 后仍返回 0，否则 CI 会产生假绿色。

## 4. GitHub Actions

`.github/workflows/ci.yml` 在 Pull Request 和 `main` 推送时：

1. 安装 .NET 10；
2. Restore；
3. Release Build；
4. 执行全部测试并保存 TRX；
5. 生成 win-x64 自包含包；
6. 上传测试结果和程序 Artifact。

CI Artifact 用于验证，不自动成为正式 Release。正式 Release 仍需版本号、说明、校验值和人工确认。

## 5. UI 冒烟清单

- Dark、Light、HighContrast 切换后文字可读；
- 字号 11–18 下顶部工具栏和标签页可用；
- 下拉列表选中项和候选项对比清晰；
- 三个模拟数据源能连接；
- CMIS 5.3/5.4 CDB 目录随 Revision 切换；
- 寄存器全景双击和右键对应正确地址；
- Blocked 写入不产生 I²C 事务；
- Critical 写入必须输入正确短语；
- 设置重启后保留；
- 断网时更新检查不影响本地功能。

## 6. 版本策略

使用 `MAJOR.MINOR.PATCH`：

- MAJOR：不兼容的 Dump、插件或工作流变化；
- MINOR：新协议、新页面、新产品化能力；
- PATCH：兼容性修复和文档修正。

版本至少同步到：

- `OptiDiag.App.csproj`；
- About 页面；
- README；
- Release 标签和标题；
- 发布包文件名。

## 7. 发布步骤

1. 工作树干净，分支基于最新 `main`；
2. 更新版本和文档；
3. Release 构建和全部测试；
4. 运行发布目录中的 EXE，而不是开发输出；
5. 压缩整个发布目录；
6. 计算 SHA-256；
7. 创建 PR，让 CI 再验证一次；
8. 合并后创建 GitHub Release；
9. 上传 ZIP并在说明中记录测试数、限制和 SHA-256；
10. 从 GitHub 下载一次，重新计算哈希并启动。

## 8. 回归优先级

最高优先级回归：

- 地址和位域错位；
- Page/Bank 串扰；
- 写入错误字段；
- 自清除字段被误判失败；
- 固件状态机自动执行 Run/Commit；
- Dump 校验失效；
- 测试失败却返回成功退出码。

其次是显示、排序、主题和文档问题。界面问题不一定破坏模块，但可能诱导用户执行错误操作，因此也需要测试和清晰提示。

## 9. 已知边界

- 模拟器测试不证明真实模块兼容；
- 规范覆盖矩阵不等于所有厂商扩展；
- 更新检查只验证 GitHub 返回的版本信息，不自动建立代码签名信任；
- 当前无真实 USB-I²C 后端；
- CI 的 Windows 虚拟机没有光模块硬件。

把边界写清楚不是示弱，而是让每个“已通过”都有准确含义。
